# D-DC. COMPANY DEVELOP
`project/company/...`의 개발 작업에 적용한다. 회사 Source의 보안·운영 안정성·추적 가능성을 속도보다 우선한다.

## D-DC.1 DEFAULT

- 기본값은 `agent_mode=auto`, `rigor=standard`이며 문서 범위는 요청·영향·검수 기준으로 자동 결정한다.
- 파일 한두 개의 국소 변경이고 기존 검증이 있으며 쉽게 되돌릴 수 있을 때만 `lean`을 사용한다.
- DB/Schema, 인증·권한·보안, 배포·운영, 공용 API, 여러 저장소, 데이터 손실 가능성, 불명확한 기준선은 `strict`로 올린다.
- 문서 Contract나 공통 규칙 변경은 직접 의존 문서까지 범위를 확장하고 Budget과 검수 기준을 명시한다.

## D-DC.2 SECURITY & OPERATION

- 회사 Source·로그·설정·데이터를 개인 프로젝트나 외부 서비스로 복제하지 않는다.
- 비밀키·계정·Token·개인정보는 Prompt, 계획, 보고서, History에 기록하지 않는다.
- 운영 배포·재시작·프로세스 종료·DB 쓰기·외부 전송은 사용자의 명시적 지시 전에는 실행하지 않는다.
- 운영 조회라도 부하 가능성이 있으면 예상 범위·상한·중단 조건을 먼저 계산하고 테스트 환경이나 제한된 표본으로 검증한다.
- 파괴적이거나 부하 상한을 모르는 운영 실험은 증거 확보 수단으로 사용하지 않는다.
- 프로젝트 내부의 더 가까운 보안·배포 규칙이 있으면 이를 우선한다.

## D-DC.3 EXECUTION

- 시작 전 브랜치, 기존 변경, 기존 실패, 빌드·테스트 기준선을 확인한다.
- `standard`: 범위 결정 → 계획 → 구현·테스트 → 완료조건 재현 순으로 진행한다.
- `strict`: 범위 결정 → 계획 → 읽기 전용 반증 → Coordinator 승인 Gate → 계획 반영 → 구현·테스트 → Coordinator 독립 검증 순으로 진행한다.
- `strict` 역할 분리는 실행 환경과 사용자가 Multi-Agent를 허용할 때만 수행하며, 아니면 Single-Agent가 단계별 Checkpoint를 명시한다.
- Worker별 목표·Source·Output·파일 소유권을 분리하고 같은 변경을 여러 Worker에게 동시에 주지 않는다.
- 계획 밖 결함은 임의로 섞어 고치지 않고 영향과 근거를 보고한다.
- 실행 가능한 명령과 불변식으로 완료를 판정하며 변하는 건수를 고정 합격선으로 사용하지 않는다.

## D-DC.4 COMPLETION

- 변경 파일과 계획 범위가 일치하는가
- 기준선 대비 새 실패가 없고 검증이 실제로 실행됐는가
- 운영·보안 승인과 미실행 항목이 명확한가
- 회사 정보와 사용자 변경이 보존됐는가
